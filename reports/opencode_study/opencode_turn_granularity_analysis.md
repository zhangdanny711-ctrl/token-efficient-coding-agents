# 交互粒度分析：turn 爆炸 = 低效碎片化吗？

日期：2026-08-06
数据：全部 16 个 clean OpenCode run（baseline/skill × F1/F3 × 4）。
方法：逐 run 重建探索阶段的**信息依赖图**——turn k 的每个调用，其目标（文件路径、符号、模式）最早在哪个 turn 的输出中可见。若 turn k 的所有调用不依赖 turn k−1 的输出，则 k 与 k−1 理论上可合并（不损失任何信息）。两种口径：
- **保守口径（相邻对合并）**：只合并相邻的无依赖 turn 对；
- **上界口径（波次调度）**：把所有调用重排为最短依赖链（wave schedule），假设单 turn 可含任意多个无相互依赖的调用。

未修改任何 benchmark 代码或 SKILL.md。

## 1. 核心答案

**是——turn 爆炸主要是交互粒度问题（碎片化），且碎片化在正常轨迹里同样存在，只是程度更轻。这是全项目迄今发现的最大浪费源。**

| | normal (n=9) | exploded (n=7) |
|---|---:|---:|
| tool-turns 实际 | 7.6 | 12.9 |
| 波次调度最少需要 | **3.0** | **3.6** |
| 可合并 turns（上界口径） | 4.6（60%） | 9.3（72%） |
| 可合并 turns（保守口径，相邻对） | 4.8 | 10.7 |
| 保守口径估算开销占总 tokens | **56%** | **77%** |

两口径给出的全样本可回收区间：**61–68% 的全部 token 消耗来自"本可合并的 turn 边界"**（16 run 合计 2.71M tokens 中的 1.66M–1.85M）。

## 2. 必要探索 vs 低效碎片化的分离

**必要串行深度只有 3–4 波**。两个任务的信息结构是：
- 波 0：`ls`/`find`/首次 pytest（只依赖 task.md）；
- 波 1：读 pytest/find 暴露的文件（F1：serializers 链；F3：spec/samples/numbers）；
- 波 2：（可选）读第一轮阅读暴露的新目标 + edit；
- 波 3：验证。

16 个 run 的波次下限都是 2–5，与轨迹是否爆炸**无关**（正常 run 均值 3.0，爆炸 3.6）。即：**爆炸 run 没有获取更深的信息链，它们只是把同一条链切得更碎。**

典型对照（F1 baseline，同任务同条件）：
- occlean3（7 turns，正常）：12 个调用打包进 6 个 tool-turn，含一个 4 调用 turn；
- occlean4（15 turns，爆炸）：14 个调用**全部单发**。手工核验其 turn 4–7 的四个连续 `read`——四个文件路径全部在 turn 2 的 `find` 输出中可见，无任何新依赖，理论上可一 turn 发出。turn 11–13 的三连 pytest 同理（同一目的的重复确认）。该 run 保守口径 87% 的 tokens 是碎片化开销。

## 3. 量化汇总（问题 2 的直接回答）

| 量 | 保守口径 | 上界口径 |
|---|---:|---:|
| 可合并 turn 数/run | 4.8（normal）～10.7（exploded） | 4.6～9.3 |
| 这些 turn 内的调用数/run | 5–16 | 同调用总量的 60–80% |
| 多余 turn 造成的 token 开销 | **1.85M / 2.71M（68%）** | 1.66M（61%） |
| 其中爆炸 run 的贡献 | 166.8k/run × 7 | 143.7k/run × 7 |
| 其中正常 run 的贡献 | 75.9k/run × 9 | 72.6k/run × 9 |

与上一份 turn 级报告（`opencode_turn_level_analysis.md`）的 62% de-batching 估算相互印证：三种独立方法（正常密度反事实、相邻对依赖、波次调度）都落在 **60–70%** 区间。

重要修正:上一份报告只把爆炸-正常**差值**归因于 de-batching；本分析显示**正常轨迹本身也有 56% 的碎片化开销**——即使消除全部爆炸，仍有一半以上 token 花在可合并的 turn 边界上。碎片化是连续谱，不是爆炸 run 的专属病理。

## 4. 四个问题的回答

**1) Turn 爆炸是真实浪费源吗？** 是，且比先前估计更大——它是"碎片化谱系"的重尾端，而碎片化本身占全部消耗的 ~2/3。

**2) 理论可回收比例？** 61–68%（两口径）。现实上界更低:合并需要模型在发出调用前就规划好一批（部分"独立"调用实际上受前一输出的语义启发,依赖判据是字符串可见性,偏宽）；打五折的现实估计仍有 ~30%,是 reads 效应（−42% reads ≈ 全局 −10% 量级）的 3 倍以上。

**3) prompt/skill 可控，还是 harness/model 行为？** 证据两面都有:
- **模型侧主导**：同一 prompt 同一条件采样出 1.13 和 1.64 调用/turn（碎片化程度是采样方差）;skill arm 与 baseline 的可合并 turn 数几乎相同（6.9 vs 7.9/run）——Skill v1 的五条规则完全没有触及粒度维度，事实上也没有影响它。
- **harness 允许打包**：12/16 run 出现过多调用 turn（最多 4 调用/turn），说明 OpenCode + GLM-5.2 技术上支持批量调用——不存在硬性 1 调用/turn 限制。
- **结论**：粒度当前是**未被任何指令约束的自由维度**，模型默认行为方差极大。prompt 能否收紧它是**可检验的开放问题**——恰好构成一个干净的 ablation：在 skill 中加入唯一一条批量指令（如"把不互相依赖的读取/命令在同一步内一起发出"），其它规则不动。若有效，粒度可控且收益上限全场最大；若无效,得到"粒度是模型采样属性、prompt 不可达"的结论——同样可发表。（按指示,此处不做设计,只指出可检验性。）

**4)（隐含）为什么 Claude Code 没这个问题？** 其 baseline 轨迹 4–9 个调用 5–9 turns，密度与 OpenCode 正常 run 相当;且其每 turn 结构成本被缓存定价大幅摊薄。碎片化的**代价**是 OpenCode+GLM 特有的（全历史每 turn 原价重发），碎片化的**行为**可能是 GLM-5.2 特有的——区分这两者需要跨模型对照，超出当前数据。

## 5. 局限

- 依赖判据是**字符串可见性**（调用目标是否在此前输出文本中出现），会漏掉语义依赖（模型读了 A 才想到查 B，即使 B 的名字早已可见）——因此可回收比例是上界族；保守口径通过只合并相邻对部分缓解，但两口径共享此偏置。真实可回收率需要干预实验（batching 指令 ablation）来测。
- turn 开销按 run 均值 turn 成本折算；实际被合并的多是中后期 turn（上下文更长、更贵），估算偏保守——两个偏置方向相反,部分抵消。
- `python3 -c` 快速验算类调用（如 F1 的 cents 换算检查）被判为独立,但其动机来自读 serializers 的语义——这类调用约占调用总量 5–8%，影响不大。
