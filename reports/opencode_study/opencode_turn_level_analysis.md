# Turn 级轨迹分析：turn 爆炸是否对应真实 token 浪费？

日期：2026-08-06
数据：全部 16 个 clean OpenCode run（baseline n=8 + skill n=8，F1/F3）。
方法：逐 turn 分段（explore / edit / verify / text-only），重复调用·重复测试·重复读取·零信息 turn 计数，以及 calls-per-turn 密度反事实估算。未提出任何修改方案。

## 一句话结论

**Turn 爆炸对应的浪费是真实的，但形态出乎意料：不是"做了多余的事"，而是"同样的事摊薄到更多 turn"。** 爆炸 run 的工具调用数只比正常 run 多 23%（15.3 vs 12.4），turns 却多 62%（13.9 vs 8.6）；其标志性特征是**逐调用单发**（85% 的 tool-turn 只含 1 个调用，正常 run 为 53%）。每多一个 turn，整段历史按缓存价重发一次——**浪费在 turn 边界本身，而不在调用内容**。

## 1. 分段结果

16 run 全部符合 explore* → edit(恰好 1 次) → verify* 的单调结构，text-only 恒为最后的总结 turn（1 个）。没有 run 出现第二次 edit 或回退。

| 段 | normal (n=9) 均值 | exploded (n=7) 均值 | Δ |
|---|---:|---:|---:|
| explore turns | 3.7 | **8.1** | **+4.4（爆炸的主体）** |
| edit turns | 1.0 | 1.0 | 0 |
| verify turns | 2.9 | 3.7 | +0.8 |
| text-only | 1.0 | 1.0 | 0 |
| 总 turns | 8.6 | 13.9 | +5.3 |
| 工具调用总数 | 12.4 | 15.3 | +2.9 |
| grand total | 134,331 | 214,612 | +80,281 |

**爆炸 = 探索阶段 +4.4 turns（84%）+ 验证阶段 +0.8 turns（16%）。** 此前 v1.1 草案把靶点放在"编辑后重复验证"，本分析证明那只是次要成分。

## 2. 经典浪费指标：几乎全部为零

| 指标 | 16 run 合计 |
|---|---:|
| 重复的相同工具调用（同签名） | **0** |
| 重复读取（同文件未修改重读） | **0**（analyzer 全 run 确认） |
| 零信息 turn（输出与历史完全重复） | **0** |
| 修复后冗余测试 turn（全量通过后再验证） | 7 次，集中于 F3（6/8 个 F3 run 各 1 次，≈14–20k tok/次），F1 爆炸 run 的三连 pytest 每次输出不同（-q tail-15 / tail-3 / 无-q），签名与信息均不同，不计为严格重复 |

**即：不存在 R3 意义上的循环、也几乎不存在 R1 意义上的重复获取。** 修复后冗余验证合计约 93k tok（7 次 × ~13k），只解释爆炸-正常总量差（562k）的 17%。

## 3. 多余 turns 的真正来源：de-batching（调用摊薄）

calls-per-turn 直方图暴露了模式:

| | 单调用 tool-turn 占比 | calls/tool-turn |
|---|---:|---:|
| normal (9 runs) | 53% | 1.64 |
| exploded (7 runs) | **85%** | 1.13 |

极端例：F1 baseline occlean3（正常，7 turns）12 个调用打包进 6 个 tool-turn（含一个 4 调用 turn）；F1 baseline occlean4（爆炸，15 turns）14 个调用**全部逐个单发**。两个 run 做的事几乎相同——occlean4 并没有读更多文件或跑更多测试，它只是每 turn 只做一件事。

反事实估算（把爆炸 run 的调用按正常密度 1.64 重新打包，每省 1 turn 按该 run 的均值 turn 成本计）：

| run | tool-turns 现状→打包后 | 省 turns | ≈ tok |
|---|---|---:|---:|
| f1_baseline_occlean4 | 14→9 | 5 | 91,978 |
| f1_skill_occlean1 | 13→8 | 5 | 87,831 |
| f3_baseline_occlean1 | 15→9 | 6 | 65,085 |
| f3_baseline_occlean3 | 10→10 | 0 | 0 |
| f3_baseline_occlean4 | 14→9 | 5 | 73,087 |
| f3_skill_occlean2 | 13→12 | 1 | 15,114 |
| f3_skill_occlean4 | 11→10 | 1 | 16,845 |
| **合计** | | | **≈350k** |

**分解：爆炸-正常总量差 562k ≈ de-batching 350k（62%）+ 冗余验证 93k（17%）+ 真实的少量额外探索调用（21%，+2.9 调用/run，这部分是信息获取，不是浪费）。**

## 4. 回答标题问题

1. **turn 爆炸对应真实浪费吗？** 是——约 79% 的爆炸超额是可去除的（de-batching + 冗余验证），只有 ~21% 是真实的额外信息获取。
2. **浪费的机制**是 OpenCode/GLM-5.2 特有的:调用打包密度是采样属性（同条件同任务能采出 1.13 也能采出 1.64），而这个 harness 的成本函数对 turn 数极其敏感（每 turn 全量历史重发）。Claude Code 上没观察到此问题——不是因为 Sonnet 不摊薄，而是其轨迹本来就短。
3. **对既有结论的影响**：
   - "turn 爆炸是环境固有方差"（8v8 附录 2）仍成立，且现在有了机制：爆炸 = 低打包密度采样。
   - 我此前 v1.1 草案的靶点（编辑后验证纪律）**只覆盖 17% 的浪费**；最大的杠杆（62%）是**调用打包/批量纪律**——一个 Skill v1 完全没有覆盖、五规则框架之外的维度。
   - 打包纪律是否 prompt 可控是全新的开放问题（它不是"别做某事"而是"把要做的事合并"，且 OpenCode 是否支持单 turn 并行工具调用需要核实——16 run 中存在 4 调用/turn 的实例，说明 harness 支持）。

## 局限

- 分段规则是启发式（edit 工具出现即 edit turn；pytest/etlkit run 即 verify），但 16 run 的单调结构使误分类风险很小。
- 反事实打包估算假设"省 1 turn = 省该 run 均值 turn 成本"，实际末期 turn 比均值贵（上下文更长），估算偏保守。
- "冗余验证"判定基于全量通过后的再验证；F1 三连 pytest 因输出不同未计入，若按语义（同一目的重复确认）计，冗余验证占比会略升。
