# AI Coding 低 Token 方法分类

本文件将论文方法转换为可讨论的机制分类。所有“候选规则”目前都是待验证假设，不是已经适用于 z code + GM 5.2 的最终 SOP。

## 1. 总体框架

端到端 token 可以粗略拆成：

```text
总 token
= 初始任务输入
+ 每轮重复携带的历史
+ 代码/文档/测试/日志等工具观察
+ 模型计划、解释、代码和总结输出
+ 失败、返工、review、重试引起的新增轮次
```

文献显示，优化重点不是单独缩短第一条 prompt，而是控制后四项，特别是历史和工具观察的重复进入。

## 2. 方法分类与证据

| 类别 | 作用机制 | 代表证据 | 证据判断 | 对固定 z code 的可控性 |
|---|---|---|---|---|
| 高信息密度任务描述 | 提前给出目标、边界、验收，减少错误假设 | Issue Ready、HULA | 对成功有中等证据；缺少直接 token 证据 | 高，用户可直接执行 |
| 条件式澄清 | 只向用户询问代码库无法回答的意图问题 | Ambig-SWE、HULA | 提高欠规格任务质量；未证明省 token | 高，但需定义触发条件 |
| 层级定位 | 从仓库结构到文件、符号、代码行逐步缩小 | Agentless、RepoCoder、CoCoGen | 对质量和上下文相关性有较强证据 | 中高，取决于工具能力 |
| 任务相关上下文裁剪 | 按当前目标保留相关代码行，过滤大段无关观察 | SWE-Pruner | 直接 token 证据最强 | 低到中，完整实现需中间件 |
| 历史压缩/旧观察折叠 | 保留状态与结论，丢弃过时的全文观察 | SWE-agent、How Agents Spend | 机制证据强 | 取决于 z code 是否支持 compaction |
| 简洁工具反馈 | 让动作效果明确，但限制无关 stdout/stderr | SWE-agent、How Agents Spend | 机制证据强 | 中，可能通过命令与指令间接控制 |
| 小范围编辑 | 输出 diff/局部修改，避免重写完整文件 | Agentless、SWE-agent | 质量与成本机制支持 | 高 |
| 条件式规划 | 直接尝试失败或任务复杂时才升级规划 | PaT、Reason-Code | 函数级直接证据；仓库级待验证 | 高 |
| 执行反馈驱动检索 | 用具体编译/测试错误决定下一次读什么 | CoCoGen、Reason-Code | 质量证据较强 | 高 |
| 提前终止 | 根据无进展或历史相似失败停止路径 | EET、SWE-agent | 直接成本/token 证据强 | 中；简单规则可直接做 |
| 选择性重试 | 保存已验证状态，只重跑失败子任务 | Runtime-Structured | 直接 retry-token 证据，但场景窄 | 中低，需要流程状态化 |
| 固定阶段工作流 | 定位—修改—验证，限制 Agent 任意漫游 | Agentless、PatchPilot | 成本与稳定性证据中等 | 高 |
| 多 Agent/静态分解 | 多角色协作或固定拆分 | MASAI、Tokenomics、Runtime-Structured | 结果混合，通信和级联重试可更贵 | 不建议作为默认规则 |
| 通用 Prompt 压缩 | 删除自然语言低信息 token | LLMLingua/LongLLMLingua | 通用场景有效；源代码场景存在质量反例 | 低，且需谨慎 |
| Skill 渐进披露 | 核心规则常驻，references 与 scripts 按需使用 | SkillReducer、SkillsBench | Skill 自身 token 有直接证据；端到端效果因 Harness 而异 | 高，可先做原型 |

## 3. 对会议三个方向的映射

### 3.1 指令编写

候选规则：

1. 用任务卡组织信息，但不追求冗长。
2. 必填：目标行为、当前行为/复现、验收标准、修改边界、禁止事项。
3. 只提供已知且相关的路径、错误和依赖；不要倾倒整个需求讨论、完整日志或无关文件。
4. 明确哪些问题需要询问用户，哪些信息应先从代码库自行搜索。

任务卡草案：

```text
目标：最终必须出现什么可观察行为？
现状：当前行为、错误或最小复现是什么？
验收：哪些测试/示例/条件表示完成？
范围：允许修改哪些区域？哪些内容不能改变？
已知线索：确认相关的文件、符号、日志片段。
决策边界：遇到哪些歧义必须先询问？
```

注意：“短”不是独立目标。Issue Ready 的结果支持短而清楚、自包含，但没有证明简单删除细节会省 token 并保持质量。

### 3.2 流程编排

候选状态机：

```text
理解验收
  ↓
低成本定位（结构/搜索/符号）
  ↓
读取最小充分上下文
  ↓
局部修改
  ↓
针对性验证
  ├─ 通过 → 必要的回归验证 → 完成
  └─ 失败 → 用新错误定向检索/修复
                    └─ 连续无进展 → 重定位或请求人工
```

关键不在于步骤数量，而在于：

- 每一步有明确输入、输出和完成条件；
- 已验证结果不因下游失败而重做；
- 新一轮必须有新增证据，否则退出当前路径；
- 简单任务不强制生成长计划；跨模块、高风险或首次验证失败时再详细规划。

### 3.3 人机交互

建议把问题分为两类：

- **应问用户**：预期行为、验收口径、业务优先级、兼容性取舍、允许的破坏性变化。
- **应由 Agent 搜索**：文件位置、函数定义、调用关系、已有测试、依赖版本、具体错误来源。

候选触发点：

1. 两个合理需求解释会产生不同外部行为；
2. 修改范围从局部扩大为跨模块/数据迁移/API 变化；
3. 连续两次修复没有新增测试通过或根因证据；
4. 需要不可逆、高风险或安全相关操作。

Ambig-SWE 表明澄清能提高欠规格任务成功率，但没有显示效率收益。因此“不确定就问”也不是低 token 规则；问题必须少、具体、可行动。

## 4. 按落地权限分层

### L0：完整 Skill 原型层

- `SKILL.md` 只保留触发、状态机、关键判断和退出规则；
- `references/` 存放只在特定任务状态下读取的详细策略与例子；
- `scripts/` 承担日志裁剪、重复动作检测、状态持久化等确定性工作；
- 不默认加载全部 references；不在每轮重复展开已知规则；
- 用 paired no-Skill / with-Skill 任务验证端到端 token 与质量。

Skill 是可快速迭代的策略原型层，不等于 Harness 的强制控制。验证有效后，再将精确观测、拦截和终止机制下沉到 z code。

### L1：无需修改 z code

- 结构化任务卡；
- 明确验收和修改边界；
- 使用 `rg`、符号和小范围读取进行层级定位；
- 先跑针对性测试；
- 用具体失败信息决定下一次搜索；
- 小范围 patch；
- 设置无进展停止/询问条件。

### L2：需要 z code 支持配置

- 限制工具输出的最大行数或只返回相关片段；
- 对旧的文件内容、日志和 observation 做结构化折叠；
- 自动检测重复读取/修改同一文件；
- 语法、类型、patch 应用 guardrail；
- 保存“已确认事实、修改状态、未决问题”的紧凑状态。

### L3：需要开发 Agent 组件

- SWE-Pruner 式任务相关代码裁剪；
- EET 式历史经验库与学习式提前终止；
- 运行时子任务图和选择性重试；
- 自动预算预测与策略路由。

会议要求是可向全员推广，因此第一版标准应优先从 L1 产生。L2/L3 可以作为平台优化建议，不能混进普通用户 SOP。

## 5. 当前可以排除的伪“最佳实践”

- “Prompt 越短越省 token”：忽略返工和后续历史成本。
- “把整个仓库/完整日志一次性给模型”：增加输入并引入噪声。
- “任何任务都先写详细计划”：简单任务可能为无收益规划付费。
- “失败就继续给更多轮次”：成功往往更早完成，高成本失败常重复读写。
- “多 Agent 天然更高效”：多 Agent 通信可能成为主要 token 消耗。
- “拆得越细越省”：静态分解可能引发级联重跑。
- “直接压缩源码 token”：可能破坏语法和实现细节。
- “只看美元费用”：缓存和输入输出价格会掩盖真实 token 变化。

## 6. 优先级建议

按“证据强度 × 无需改工具 × 潜在收益”排序：

1. 减少重复读取和重复修改；
2. 限制无关工具输出，保留简洁、可行动反馈；
3. 层级定位后再读取代码；
4. 无进展时提前停止当前路径；
5. 失败后只补充错误相关上下文；
6. 简单任务条件式规划，复杂任务再完整规划；
7. 用高信息密度任务卡减少需求误解；
8. 对真正的需求欠规格进行一次集中澄清。

其中 1–5 有较强直接或机制证据；6–8 需要在 z code + GM 5.2 下重点验证。
