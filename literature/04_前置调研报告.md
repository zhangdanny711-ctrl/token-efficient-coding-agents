# 固定模型与工具链下的 AI Coding 低 Token 方法前置调研

版本：v0.2  
日期：2026-07-21  
适用场景：z code + GM 5.2（模型与工具链固定）

## 摘要

本调研围绕“在任务质量基本相同的情况下，如何减少 AI Coding 的 token 消耗”开展范围综述。候选池包含 44 篇论文，核心精读 18 篇，覆盖 token 成本分析、代码上下文管理、Agent 流程、规划与验证、工具接口、人机交互以及 Agent Skill。

调研结论是：**该方向具备继续研究和抽象为操作规范的可行性，但现有证据不足以直接发布一套通用最佳实践。** 当前最一致的证据并不支持“单纯把 prompt 写短”，而是指向三个主要浪费源：

1. 当前决策不再需要的历史、代码和工具输出仍反复进入输入；
2. 失败轨迹中的重复文件读取、重复修改和无进展 review/repair 循环；
3. 不根据任务复杂度和当前进展调整规划、搜索、候选生成、验证与停止策略。

直接研究显示，任务相关的代码上下文裁剪可在若干 Coding Agent 基准上减少约 23%–38% token 且不降低成功率；经验驱动的提前终止平均减少约 30% 输入 token；只重试失败子步骤在受控案例中显著降低 retry token。与此同时，静态任务分解、通用 prompt 压缩、无条件详细规划和无条件人机交互都存在反例或证据空白。

因此，后续研究应优先围绕“高信息密度任务描述—层级定位—最小充分上下文—局部修改—针对性验证—无进展退出”形成候选规则。完整 Skill（SKILL.md、references、scripts）适合作为低成本策略原型层；经过固定环境验证的强制控制与精确观测再下沉至 z code Harness。

## 1. 背景与问题定义

会议提出的研究边界是固定模型、固定工具链，目标是输出可供全员使用的低 token、高质量 AI Coding 操作规范。这意味着模型训练、模型路由和价格优化不在核心范围内；研究对象应是用户与 Agent 之间可观察、可重复的行为。

本报告将“token 效率”定义为：在相同任务质量约束下，减少完成任务过程中所有模型调用的输入、输出及可见 reasoning token。美元成本、延迟、工具调用次数和人工时间是辅助指标，不能替代 token 本身。

需要特别区分：

- 初始 prompt token；
- 每轮重复携带的对话和文件历史；
- 工具返回的代码、日志、测试输出；
- 模型生成的计划、解释、代码和总结；
- 因失败和返工新增的调用。

如果只压缩初始 prompt，却让 Agent 多读文件、多失败两轮，端到端 token 可能反而增加。

## 2. 调研方法

检索覆盖 arXiv、ACL Anthology、OpenReview、会议官方页和作者项目页，Coding Agent 主检索截止 2026-07-20，Skill 专项补充截止 2026-07-21。采用范围综述和前后向滚雪球，不声称穷尽全部相关论文。

文献按三档分级：

- A：Coding Agent/代码任务，同时报告质量和 token/成本，有对照或消融；
- B：直接研究 Coding，但 token 只通过成本、轮次或上下文间接体现；
- C：通用压缩、评测或相邻任务，需要迁移验证。

详细检索式、44 篇候选池和纳入排除标准见《01_文献检索与筛选记录》。

## 3. 主要发现

### 3.1 最大问题是累积输入，而不是最终回答

[How Do AI Agents Spend Your Money?](https://arxiv.org/abs/2604.22750) 在 OpenHands、8 个模型和 SWE-bench Verified 上保存完整执行轨迹。论文发现，Agentic Coding 的 token 远高于单轮代码推理和普通代码聊天，差异主要来自完整历史、代码和工具观察在每一轮被重新输入。其 phase 分析显示，文件查看、测试执行等动作会把大量新内容加入上下文；即使有缓存，累计输入仍可能主导总体成本。

[Tokenomics](https://arxiv.org/abs/2601.14470) 在 ChatDev 的 30 个任务中得到相似方向：输入 token 平均占 53.9%，Code Review 阶段平均占总 token 的 59.4%。由于该研究只有一个多 Agent 框架，这两个具体比例不能外推到 z code，但它清楚展示了反复传递完整代码和 review 对话的“communication tax”。

由此得到的可靠判断是：**研究优先级应从“怎么缩短用户第一句话”转向“Agent 后续每轮重新看了什么”。**

### 3.2 高成本失败通常不是更深入，而是更重复

How Do AI Agents Spend 的同任务重复运行分析发现，准确率从最低成本提升到中等成本后趋于饱和；更贵的运行中，重复查看和修改同一文件显著增加。也就是说，额外 token 经常表示路径失控，而不是有效深入。

[SWE-agent](https://arxiv.org/abs/2405.15793) 得到“成功得快、失败拖得久”的行为观察：成功运行通常更早提交、更便宜，接近预算上限的运行成功概率较低。其 ACI 设计进一步说明，简单动作、紧凑操作、简洁但充分的反馈、语法 guardrail 和旧 observation 折叠都能帮助 Agent 少走弯路。

[EET](https://arxiv.org/abs/2601.05777) 提供了目前最直接的停止证据：跨三种 Agent 和两个模型，提前终止使 API 调用、输入 token、输出 token 平均下降 20.8%、29.9%、25.1%，总成本平均下降 31.8%，最大 resolve-rate 损失为 0.2 个百分点。但 EET 依赖历史经验库，论文的节省比例不能直接套用于没有历史数据的团队。

可迁移机制不是“设一个很小的硬预算”，而是：**新一轮如果没有新增根因证据、通过更多测试或缩小假设空间，就不应沿相同路径继续。**

### 3.3 代码上下文需要任务相关且保持结构

[SWE-Pruner](https://arxiv.org/abs/2601.16746) 是本轮最强的上下文—token 直接证据。它在 Agent 与环境之间增加任务相关、行级代码裁剪，在 SWE-bench Verified 上减少 23%–38% token，同时成功率提高 1.2–1.4 个百分点；在 SWE-QA 上下降 29%–54%，多数配置质量变化很小。论文还观察到，读取操作占 token 的 67.5%–76.1%。

但它也提供了重要反例：通用 token 级压缩和粗粒度 RAG 可能破坏语法或遗漏实现细节，导致成功率下降。因此“把代码压缩到越短越好”不是正确规范。

[RepoCoder](https://arxiv.org/abs/2303.12570) 和 [CoCoGen](https://aclanthology.org/2024.findings-acl.138/) 进一步支持两个原则：

- 从仓库结构、文件、符号到代码行逐步缩小，而不是一次读完整仓库；
- 利用第一次生成、编译或测试的具体错误改进下一次检索，而不是无目标扩展上下文。

因此，上下文优化的目标应是“最小充分且结构完整”，不是“最少字符”。

### 3.4 有效的是条件式流程，不是步骤越多越好

[Agentless](https://arxiv.org/abs/2407.01489) 的“定位—修复—验证”和 [PatchPilot](https://arxiv.org/abs/2502.02747) 的“复现—定位—生成—验证—精炼”说明，规则化阶段可以用较可控的成本完成仓库级修复。真正有迁移价值的是阶段完成条件、层级定位和小范围 patch，而不是照搬论文的采样次数。

[Runtime-Structured Task Decomposition](https://arxiv.org/abs/2605.15425) 明确推翻了“任务拆细天然省 token”。在其受控案例中，静态分解因级联重跑，retry cost 比单体 prompt 更高；只有保存已验证状态、只重试失败子任务时才明显降低重试成本。

[PaT](https://aclanthology.org/2026.acl-long.1703/) 和 [Reason-Code](https://aclanthology.org/2026.acl-industry.30/) 则说明，规划和高级搜索应由失败信号触发。简单任务直接生成并做低成本验证，失败后再规划，可能优于所有任务都先支付规划成本。由于两篇主要使用函数/竞赛级任务，这一原则在仓库级 z code 场景仍需验证。

综合来看，推荐研究的不是一条僵硬流水线，而是具备以下触发条件的状态机：

```text
理解验收 → 低成本定位 → 最小上下文 → 局部修改 → 针对性验证
                                                    ↓失败
                              用新错误补充上下文/修复
                                                    ↓无进展
                                         重定位或询问用户
```

### 3.5 好任务描述强调信息密度，澄清强调必要性

[What Makes a GitHub Issue Ready for Copilot?](https://arxiv.org/abs/2512.21426) 分析 3,180 个 Copilot PR，发现较短、范围清楚、自包含、无歧义、给出相关 artifact 与实现方向的 issue 与更高 merge rate 相关。它是观察性研究，不能证明这些属性直接降低 token，但支持“高信息密度任务卡”，不支持堆砌大量背景材料。

[HULA](https://arxiv.org/abs/2411.12924) 的 Atlassian 部署表明，工程师在计划和代码阶段补充上下文具有实践价值，尤其适合简单任务和启动工作；同时代码质量仍需人工关注。

[Ambig-SWE](https://arxiv.org/abs/2502.13069) 发现，欠规格任务中一次具体、可行动的澄清可大幅提高成功率，但模型通常不会主动问，而且论文明确没有观察到效率收益。有效问题集中在预期行为和任务要求；文件位置等可从仓库搜索的信息，询问用户的价值较低。

因此，人机协作规则应是：

- 缺少目标、验收、业务边界和兼容性取舍时问用户；
- 文件位置、调用关系、现有测试和错误来源先由 Agent 搜索；
- 将澄清定位为质量保障机制，不能未经验证声称它一定省 token。

### 3.6 Skill 是可行的策略载体，但不是天然的 Token 优化器

[SkillsBench](https://arxiv.org/abs/2602.12670) 将 Skill 定义为必需 SKILL.md、可选 scripts、references 和 assets 的程序知识包，并在 87 个任务、18 个模型—Harness 配置上做 matched 对照。Curated Skills 使平均通过率从 33.9% 提高到 50.5%，但各配置 token 有增有减；同一模型换 Harness 后收益也会变化。这说明 Skill 可以改变 Agent 行为和质量—成本前沿，但“使用 Skill”不能直接推出 raw token 下降。

[SkillReducer](https://arxiv.org/abs/2603.29919) 则直接研究 Skill 自身的上下文开销。它在 55,315 个公开 Skill 中发现大量非可执行正文和可能一次注入数万 token 的 references，并通过路由压缩、核心规则提取和渐进披露报告 description 下降 48%、body 下降 39%、最佳设置端到端输入下降 26.8%，功能质量提高 2.8%。它支持“短而可执行的核心 + 按需 references + scripts”的结构，但没有证明一个 Skill 能自动消除 Coding Agent 的无进展循环或非自适应预算。

[How Well Do Agentic Skills Work in the Wild](https://arxiv.org/abs/2604.04323) 进一步显示，Skill 从大规模真实库中检索时，收益会随匹配度下降而变脆弱；任务相关 refinement 只能在初始 Skill 已经相关且质量可接受时恢复收益。因此第一版应做范围明确、直接触发的单一 Skill，不应先构建庞大 Skill 库。

当前研究缺口位于两条文献线的交叉处：Skill 研究主要关注程序知识包的质量、路由和自身 token；Coding Agent 效率研究分别验证上下文裁剪、提前终止和条件式预算。尚缺一个完整 Skill 在固定 Coding Agent 上同时整合三类机制，并以任务质量约束下的端到端 token 做配对验证。

## 4. 哪些结论可以与不可以迁移

### 可以作为第一批候选规范

1. 任务描述包含目标、现状/复现、验收、范围和禁止事项，但避免无关材料。
2. 先搜索仓库结构和符号，再读取小范围代码。
3. 工具输出只保留与当前判断相关的代码、错误和日志段。
4. 使用局部 patch，避免无必要的整文件重写。
5. 先跑最便宜且最相关的测试，再扩大验证范围。
6. 每轮失败必须带来新证据；连续无进展则停止当前路径。
7. 简单任务不强制长计划，验证失败或跨模块时再升级规划。
8. 只向人询问代码库无法回答的需求决策。
9. Skill 只常驻核心可执行规则，references 与 scripts 按当前状态使用，不默认全部加载。

### 需要 z code 平台支持

1. 对旧文件内容、日志和工具 observation 自动折叠；
2. 检测重复查看、重复修改和无进展循环；
3. 任务相关的行级代码裁剪；
4. 保存已验证子任务状态并选择性重试；
5. 基于历史 trajectory 的学习式提前终止。

### 当前不能作为结论

- Prompt 越短越好；
- 总是先做详细计划；
- 多 Agent 一定比单 Agent 省；
- 拆分步骤越多越高效；
- 允许更多 token 会提高成功率；
- 通用自然语言压缩器适合直接压缩源代码；
- 人工交互一定减少 token。
- 只要启用 Skill 就一定减少端到端 token。

## 5. 证据风险

最主要的证据风险来自评测集。大量研究使用 SWE-bench Lite/Verified，但公开题目、gold patch 和测试长期暴露，且部分测试会拒绝合理修复。OpenAI 在 2026 年的审计中也指出测试缺陷与污染问题：[Why SWE-bench Verified no longer measures frontier coding capabilities](https://openai.com/index/why-we-no-longer-evaluate-swe-bench-verified/)。

因此，本报告引用这些论文时只关注同一设置内“加/不加某机制”的相对变化，不使用跨论文排行榜推导优劣。未来如果验证 z code，应优先使用冻结 commit、客观验收和未公开内部任务。

另一个风险是成本指标混用。缓存 token 单价、输入输出价格和模型路由会让美元成本与 token 数量不一致。后续研究至少需要分别记录 input、cached input、output、reasoning、调用次数和轮次。

## 6. 可行性判断

结论：**Go，但应缩小研究主张。**

可以形成标准化框架的部分：

- 任务输入结构；
- 代码定位与上下文选择顺序；
- 工具输出控制；
- 规划和验证的条件式触发；
- 无进展判断与人工升级；
- Skill 的核心规则、按需 references 与确定性 scripts 的职责边界。

暂时不能形成全员规则的部分：

- 精确 token 节省比例；
- 学习式 pruner/EET 等需要工程接入的方法；
- 对所有任务统一适用的最大轮次或最大 token；
- 多 Agent 和人机交互的普遍效率结论。

换言之，文献足以提出一套“候选操作协议”，但不足以证明其在 z code + GM 5.2 下已经成立。下一阶段的价值不是从零试错，而是验证少数已有证据支持、且团队可以实际控制的规则。

## 7. 建议的调研交付口径

向 mentor 汇报时建议使用以下表述：

> 现有研究支持把 AI Coding 的低价值 token 归纳为三类机制：当前决策不需要的冗余上下文、没有新增证据的执行循环，以及不随任务状态调整的资源分配。任务相关上下文裁剪、提前终止和选择性重试存在直接的质量—token 证据；条件式规划、任务卡和人机澄清存在质量或成本机制证据。Skill 研究进一步证明，聚焦、渐进披露的程序知识包可以减少 Skill 自身开销并提升部分任务质量，但尚未证明一个完整 Skill 能在固定 Coding Agent 上同时解决三类问题。因此该方向具备继续推进价值，下一步应在 z code + GM 5.2 上做 no-Skill / with-Skill 配对验证。
