# 核心论文阅读卡

说明：以下“论文证据”尽量保留作者的实验边界；“本项目推论”是针对 z code + GM 5.2 的迁移判断，不等同于论文原结论。检索截止 2026-07-20。

## 1. How Do AI Agents Spend Your Money?（Bai et al., 2026）

- 原文：[arXiv:2604.22750](https://arxiv.org/abs/2604.22750)
- 研究问题：Coding Agent 的 token 花在哪里；同任务重复运行是否稳定；更多 token 是否带来更高成功率。
- 方法：OpenHands；SWE-bench Verified 500 题；8 个前沿模型；每个问题 4 次独立运行；保留完整 trajectory 和逐轮 usage。
- 论文证据：Agentic Coding 平均比单轮代码推理和多轮代码聊天分别消耗约 3500 倍和 1200 倍 token，差异主要来自不断累积并重复发送的输入上下文。同一模型处理同一问题时，最贵运行通常约为最便宜运行的 2 倍；准确率在中等成本附近达到峰值，继续增加 token 后饱和。高成本运行与重复查看、重复修改同一文件显著相关。
- 关键机制：完整历史在每轮原样带回；文件查看、测试输出和历史缓存累计形成输入主导的成本。
- 局限：单一 Agent scaffold；虽然覆盖 8 个模型，但不能代表所有 Agent 设计；使用 SWE-bench Verified。
- 本项目推论：优先控制重复文件读取、重复修改、长日志和失败后的无界循环；不能把“给更高 token 预算”当作质量保证。
- 证据等级：A。

## 2. Tokenomics（Salim et al., 2026）

- 原文：[arXiv:2601.14470](https://arxiv.org/abs/2601.14470)
- 研究问题：多 Agent 软件开发生命周期中，各阶段分别消耗多少 input、output 和 reasoning token。
- 方法：ChatDev + GPT-5 Reasoning；30 个软件开发任务；将内部 phase 映射为设计、编码、补全、审查、测试和文档。
- 论文证据：Code Review 阶段平均占总 token 的 59.4%；总体 token 中输入、输出、reasoning 平均占 53.9%、24.4%、21.6%。作者将多 Agent 反复传递完整代码称为“communication tax”。
- 局限：work-in-progress；仅一个多 Agent 系统和一个模型；部分阶段样本很小，如 Code Completion 只有 6 次、Testing 只有 12 次。
- 本项目推论：结论不能直接套到单 Agent z code，但支持优先调查“历史/代码反复进入输入”和“review/refine 循环”。
- 证据等级：A（直接测 token，但外部有效性有限）。

## 3. EET: Experience-Driven Early Termination（Guo et al., 2026）

- 原文：[arXiv:2601.05777](https://arxiv.org/abs/2601.05777)
- 研究问题：能否利用历史执行经验，提前终止无效的补丁生成和选择。
- 方法：SWE-bench Verified；Agentless、Mini-SWE-Agent、Trae Agent；GPT-5-mini 与 DeepSeek-V3.2；结构化历史经验检索 + 终止判断。
- 论文证据：总成本下降 19.3%–55.1%，平均 31.8%；API 调用、输入 token、输出 token 平均下降 20.8%、29.9%、25.1%；最大任务成功率损失 0.2 个百分点。简单 bug-fix 比复杂 feature 更容易获得终止收益。
- 局限：依赖历史数据，存在 cold start；仅在 SWE-bench Verified；离线生成经验的成本未计入单任务成本。
- 本项目推论：可以先实现不依赖额外模型的弱版本，例如“连续两轮没有新增证据/测试进展则停止当前路径并重新定位或询问人”。不能直接声称可复制论文的 31.8%。
- 证据等级：A。

## 4. SWE-Pruner（Wang et al., 2026）

- 原文：[arXiv:2601.16746](https://arxiv.org/abs/2601.16746)
- 研究问题：如何在不破坏代码结构的情况下，对 Coding Agent 收到的长代码观察做任务相关的行级裁剪。
- 方法：0.6B neural skimmer 作为 Agent—环境中间件；Mini-SWE-Agent/SWE-bench Verified 与 OpenHands/SWE-QA；多模型对照。
- 论文证据：SWE-bench Verified 上 token 下降 23%–38%，成功率提高 1.2–1.4 个百分点，轮次下降 18%–26%；SWE-QA 上 token 下降 29%–54%，质量变化较小但个别配置有轻微下降。论文分析中，读取操作占 token 的 67.5%–76.1%。
- 重要反例：通用 token 级压缩 LLMLingua2 和粗粒度 RAG 在作者的 SWE-bench 子实验中明显降低成功率；说明“压得更多”不等于更好。
- 局限：主要是 Python；引入额外模型与延迟；部分评价使用 LLM-as-a-Judge；依赖新的 Agent 中间件。
- 本项目推论：最值得迁移的是“带明确当前目标的结构化/行级筛选”，而不是生硬截断代码或把自然语言压缩器直接用于源代码。
- 证据等级：A。

## 5. Runtime-Structured Task Decomposition（Asthana et al., 2026）

- 原文：[arXiv:2605.15425](https://arxiv.org/abs/2605.15425)
- 研究问题：任务分解本身是否省 token；失败时只重跑失败子任务能否降低重试成本。
- 方法：两个软件工程 workload；monolithic、static decomposition、runtime-structured 三组；每组 10 次。
- 论文证据：静态分解不一定省成本。在 Kubernetes RCA 场景中，静态分解重试成本比单体 prompt 高 80.5%，因为下游步骤被级联重跑；只重试失败子任务相对单体和静态分解最多下降 51.7% 和 73.2%。
- 局限：只有两个受控案例；温度为 0；自然失败率仅 0–2%，主要用模拟失败计算重试；runtime 方案基线成本更高。
- 本项目推论：不要把“把任务拆成更多步骤”直接写成省 token 规范。有效机制是保存已验证状态、隔离失败、只重做必要部分。
- 证据等级：A，但样本与场景较窄。

## 6. PaT: Planning-after-Trial（Yoon et al., 2026）

- 原文：[ACL Anthology](https://aclanthology.org/2026.acl-long.1703/)
- 研究问题：所有题目都在生成前规划是否浪费计算；能否只在直接尝试验证失败后调用 planner。
- 方法：HumanEval、MBPP、xCodeEval 等函数/竞赛级基准；比较直接生成、Planning-before-Trial 与 Planning-after-Trial；同时研究异构模型配置。
- 论文证据：按失败触发规划改善成本—性能前沿；其异构配置达到接近大模型同构配置的性能，同时相对成本约为 31%，即约降 69%。
- 局限：主要是函数/竞赛代码，不是仓库级 Agent；最大节省依赖大小模型组合，而本项目固定 GM 5.2；自生成测试可能误触发规划。
- 本项目推论：只能迁移“条件式规划”假设，不能迁移 69% 数字。简单、验收明确的任务可先进行低成本定位/尝试，失败或跨模块时再升级为详细计划。
- 证据等级：A（直接成本证据，场景迁移有限）。

## 7. Reason-Code（Li & Peng, 2026）

- 原文：[ACL Anthology](https://aclanthology.org/2026.acl-industry.30/)
- 研究问题：能否在 greedy 生成失败后才启用执行反馈搜索，从而避免 Best-of-N 的固定成本。
- 方法：HumanEval 和 MBPP；greedy、Best-of-N、Reflexion、MCTS；单位测试反馈；条件式预算。
- 论文证据：Adaptive Reason-Code 约以 greedy 1.5 倍的平均 token 成本达到或超过高成本采样基线；在低预算下，执行反馈的自适应推理明显优于独立采样，但复杂 MCTS 并未稳定优于简单迭代修复。
- 局限：依赖测试覆盖；基准较小且主要一个模型族；函数级任务；低预算下无法证明复杂搜索控制器的独立价值。
- 本项目推论：先直接尝试并跑便宜、针对性的验证，失败后再增加搜索预算；没有证据支持默认多采样或复杂树搜索。
- 证据等级：A。

## 8. SWE-agent（Yang et al., 2024）

- 原文：[arXiv:2405.15793](https://arxiv.org/abs/2405.15793)
- 研究问题：固定模型时，Agent-Computer Interface（ACI）怎样改变仓库导航、编辑和测试行为。
- 方法：自定义文件查看、搜索、编辑和反馈接口；SWE-bench/HumanEvalFix；多项接口消融。
- 论文证据：有效 ACI 原则包括：动作简单；一次动作完成有意义进展；反馈信息充分但简洁；用 lint 等 guardrail 加快错误恢复；旧观察折叠以减少无关历史。论文还发现“成功得快、失败拖得久”：成功轨迹通常更早、更便宜；增加最大预算未必提高表现。
- 局限：论文主要验证性能与美元成本，不是专门的 token 优化研究；最初围绕 GPT-4 Turbo 设计；旧版 SWE-bench 绝对分数已不宜作为当前能力结论。
- 本项目推论：如果 z code 可配置工具输出和历史，应优先采用简洁工具反馈、旧观察折叠和编辑 guardrail；如果不可配置，只能通过用户指令间接约束。
- 证据等级：B。

## 9. Agentless（Xia et al., 2024）

- 原文：[arXiv:2407.01489](https://arxiv.org/abs/2407.01489)
- 研究问题：复杂自主 Agent 是否必要；固定“定位—修复—验证”流程能否更稳定、更低成本。
- 方法：层级定位文件/类/函数/行；生成多个 diff；回归与复现测试筛选；SWE-bench Lite。
- 论文证据：论文报告 32.0% resolve rate、平均成本约 0.70 美元；层级定位优于直接把完整文件交给模型；小范围 diff 避免重写完整代码。
- 局限：绝对结果来自已出现测试缺陷和污染争议的公开基准；批量采样多个定位与补丁本身也会增加 token；不覆盖一般功能开发。
- 本项目推论：可迁移的是层级定位和小范围修改，不应简单推导为“禁用 Agent 自主性”。
- 证据等级：A/B。

## 10. PatchPilot（Li et al., 2025）

- 原文：[arXiv:2502.02747](https://arxiv.org/abs/2502.02747)
- 研究问题：如何在完全自主规划与过于僵硬的固定流程之间平衡性能、稳定性和成本。
- 方法：复现—定位—生成—验证—精炼五阶段规则化工作流；组件消融；SWE-bench Lite/Verified。
- 论文证据：论文报告 Lite 45.33%、Verified 53.60%，平均每题约 1 美元以内；精炼阶段在消融中进一步提高解决数。
- 局限：主要报告美元成本而非 token；多次定位、候选生成和最多 7 次复现会增加资源；公开基准绝对分数不可直接外推。
- 本项目推论：阶段化和明确退出条件具有可迁移性；“精炼”必须由新测试证据驱动，否则容易变成无界 review loop。
- 证据等级：A（成本）/B（token）。

## 11. RepoCoder（Zhang et al., 2023）

- 原文：[arXiv:2303.12570](https://arxiv.org/abs/2303.12570)
- 研究问题：如何利用第一次生成结果改进第二次仓库检索，使检索内容更接近目标代码。
- 方法：检索—生成迭代；RepoEval；行、API、函数体补全。
- 论文证据：相对只看当前文件的 baseline，EM 绝对提升超过 10%；两轮通常优于普通一次 RAG。检索质量和生成质量显著相关。
- 局限：低代码重复仓库收益有限；最佳迭代次数不稳定；额外迭代增加延迟，论文没有以 token 为主要优化目标。
- 本项目推论：初始搜索不必一次完美，可用初次假设改写下一次检索；但应设置停止条件，不能把“迭代检索”无限化。
- 证据等级：B。

## 12. CoCoGen（Bi et al., 2024）

- 原文：[ACL Anthology](https://aclanthology.org/2024.findings-acl.138/)
- 研究问题：能否用编译器的具体错误，按需检索缺失的项目上下文并修复代码。
- 方法：生成—编译/静态分析—检索错误相关仓库信息—修复；GPT-3.5-Turbo 与 Code Llama 13B。
- 论文证据：对依赖项目上下文的函数生成，相对 vanilla LLM 的 pass rate 提升超过 80%，并优于普通检索基线。
- 局限：主要是 Python/函数级；关注准确率，不直接报告 token 节省；循环可能增加调用。
- 本项目推论：验证反馈应转化为针对性检索，而不是重新读取整个仓库；收益来自“错误驱动的上下文补充”，不是迭代本身。
- 证据等级：B。

## 13. HULA（Takerngsaksiri et al., 2024）

- 原文：[arXiv:2411.12924](https://arxiv.org/abs/2411.12924)
- 研究问题：计划和代码生成阶段加入软件工程师反馈，在企业 Jira 流程中是否有价值。
- 方法：Atlassian 部署；Planner、Coding、Human 三角色；SWE-bench、369 个内部 issue、663 个线上 issue、109 份问卷。
- 论文证据：线上 527 个成功生成的计划中 433 个获批，计划批准率 82%；工程师认为对简单任务、启动计划和初始代码有帮助。论文同时指出，输入细节显著影响表现，代码质量仍是主要担忧。
- 局限：没有 token 指标；内部实现不能完全披露；仅 GPT-4；代码相似度和问卷不能等同于功能正确。
- 本项目推论：人工介入应优先用于补全缺失需求和批准高风险计划，而不是每一步审查。其 token 效果需要另行验证。
- 证据等级：B。

## 14. What Makes a GitHub Issue Ready for Copilot?（Sayagh, 2025）

- 原文：[arXiv:2512.21426](https://arxiv.org/abs/2512.21426)
- 研究问题：什么样的 GitHub issue 更可能让 Copilot 生成最终被合并的 PR。
- 方法：3,180 个 Copilot PR 及其 issue；32 个可解释质量标准；合并/关闭关联分析与预测模型。
- 论文证据：较短、范围清楚、自包含、无歧义、指出相关 artifact 和实现方向的 issue 与更高 merge rate 相关；预测模型中位 AUC 72%。外部配置/API/依赖信息负担与更低 merge rate 相关。
- 局限：观察性关联而非随机实验；只研究 Copilot；“被合并”同时受项目和评审者影响，不等同于代码质量或 token 效率；32 个标准由 LLM 评分。
- 本项目推论：任务卡应追求高信息密度而不是长；至少写清目标、边界、验收、已知相关位置和不可做事项。但不能据此声称一定省 token。
- 证据等级：B。

## 15. Ambig-SWE（Vijayvargiya et al., 2026）

- 原文：[arXiv:2502.13069](https://arxiv.org/abs/2502.13069)
- 研究问题：Agent 能否检测欠规格需求、提出有价值的问题并利用用户回答提高任务成功率。
- 方法：将 SWE-bench Verified 改写为欠规格版本；比较完整、欠规格无交互、欠规格有交互；多模型。
- 论文证据：交互相对无交互最高可提升 74%；模型通常不会主动澄清，提示措辞会强烈影响是否询问。最有效的问题是具体、可行动、需求级的问题；代码库可自行搜索出的实现细节价值较低。
- 重要反例：作者明确指出，交互改善任务成功，但没有表现出效率收益。
- 局限：欠规格任务与用户回答均为合成；前三轮内衡量是否澄清；用户模拟器可能比真人更配合；仍基于 SWE-bench Verified。
- 本项目推论：只在缺少“用户意图/验收/边界”时问人；文件位置和实现细节应先搜索代码库。澄清是质量机制，不应未经验证包装成省 token 机制。
- 证据等级：B。

## 16. SkillsBench（Li et al., 2026）

- 原文：[arXiv:2602.12670](https://arxiv.org/abs/2602.12670)
- 研究问题：完整 Agent Skill（必需的 SKILL.md，可选 scripts、references、assets）在不同模型和 Harness 上是否真正改善任务结果，以及成本效果是否稳定。
- 方法：87 个可确定性验证的真实任务；OpenHands、Codex、Claude Code、Gemini CLI 等 18 个模型—Harness 配置；同任务 matched no-Skills 与 curated-Skills 对照，每个条件目标为 3 次运行。
- 论文证据：curated Skills 的平均通过率由 33.9% 提高到 50.5%（+16.6 个百分点），但配置收益跨度为 +4.1 至 +25.7 个百分点。最多 3 个模块的聚焦 Skill 优于庞大、穷尽式 Skill。Token 结果高度异质：18 个配置中既有下降，也有基本持平和显著上升，因此 Skill 不是天然的 raw-token 节省器。
- 关键机制：Skill 通过 Harness 的发现、加载、工具和执行循环产生作用；同一模型换 Harness 后收益会变化。论文还发现临时自生成 Skill 在三个专用 Harness 配置上均低于 no-Skills baseline，说明高质量、预先验证的程序知识不能由运行中随手生成替代。
- 局限：跨 8 个领域，不专门针对仓库级修复；不同提供方 token 计量口径并不完全相同，Claude Code 统计为近似；最新版本仍是 2026 年预印本。
- 本项目推论：必须用固定 z code + GM 5.2 做 matched paired evaluation；评价指标应是成功率约束下的端到端 token，而不是仅看 Skill 是否被触发或 Skill 文件有多短。
- 证据等级：A。

## 17. SkillReducer（Gao et al., 2026）

- 原文：[arXiv:2603.29919](https://arxiv.org/abs/2603.29919)
- 研究问题：如何减少 Skill 路由描述、正文和 references 带来的运行时上下文开销，同时保留触发正确性和功能质量。
- 方法：分析 55,315 个公开 Skill；在 600 个 Skill 上评价两阶段优化：先压缩/修复 description 路由层，再将正文分类为核心规则和按需 references，并用触发、忠实度与任务验证门控恢复被误删内容。
- 论文证据：公开 Skill 中 26.4% 缺失路由描述，超过 60% 的正文非可执行，references 单次可能注入数万 token。方法报告 description 压缩 48%、body 压缩 39%，最佳设置端到端输入节省 26.8%，功能质量提高 2.8%。
- 关键机制：渐进披露不是简单删字，而是把始终需要的可执行规则保留在核心层，把详细说明和资料改为任务触发后按需加载；验证失败时恢复关键信息。
- 局限：压缩过程每个 Skill 需要 20–40 次 LLM 调用，收益依赖长期复用摊销；600 个 Skill 的任务分布不等同于仓库级 Coding；论文仍是较新的预印本。
- 本项目推论：`token-efficient-coding` 必须保持短而可执行的 SKILL.md、显式 reference 路由和可直接运行的 scripts；不能把整份调研报告塞进 Skill，也不能仅以 Skill 文件压缩率作为成功指标。
- 证据等级：A。

## 18. How Well Do Agentic Skills Work in the Wild（Liu et al., 2026）

- 原文：[arXiv:2604.04323](https://arxiv.org/abs/2604.04323)
- 研究问题：当 Agent 必须从约 34K 个真实 Skill 中自行检索，且候选 Skill 不一定与任务精确匹配时，Skill 的收益是否仍然存在。
- 方法：逐步增加检索和匹配难度，比较直接提供精选 Skill、从真实池检索、query-specific refinement 和 query-agnostic refinement；并迁移到 Terminal-Bench 2.0。
- 论文证据：Skill 收益会随着检索池扩大和任务匹配度下降而衰减，最困难设置接近 no-Skills baseline；当初始 Skill 相关且质量可接受时，query-specific refinement 可恢复明显收益。在 Terminal-Bench 2.0 上，Claude Opus 4.6 通过率从 57.7% 提高到 65.5%。
- 局限：重点是成功率而非 token；检索与 refinement 本身增加模型调用；没有直接研究无进展循环或 Coding Agent 动态预算。
- 本项目推论：第一版应使用一个明确触发、范围窄的 Skill，而不是大规模 Skill 库；references 的选择应由当前任务和当前状态决定，不能把所有材料默认加载。
- 证据等级：B。

## 19. Skill-to-LoRA（Zhang & Qi, 2026）

- 原文：[arXiv:2606.16769](https://arxiv.org/abs/2606.16769)
- 研究问题：能否把 Skill 文本引起的行为变化训练进 LoRA，从而避免每步重复注入完整 SKILL.md。
- 方法：Qwen3.6-27B；SWE-Skills-Bench 的 21 个 Skill；比较 no-skill、Full Skill Text 与 skill-specific LoRA。
- 论文证据：相对 Full Skill Text，每步 token 下降 6.6%，通过率提高 5.2 个百分点；错误或共享 LoRA 会降低表现，说明收益依赖技能与 adapter 对齐。
- 局限：需要可训练模型和离线示范生成；仅 21 个 Skill、单一基础模型；代码尚待论文接收后发布；不适用于无法微调的固定闭源 GM 5.2。
- 本项目推论：它证明“重复注入 Skill 文本本身也是成本”，但只作为边界证据；本项目应优先使用渐进披露、scripts 和 Harness 缓存/状态，而不是训练模型。
- 证据等级：C。

## 横向结论

| 结论 | 支持强度 | 主要依据 |
|---|:---:|---|
| 输入历史、文件读取和工具输出是首要 token 优化对象 | 强 | How Agents Spend、Tokenomics、SWE-Pruner |
| 无效长轨迹常伴随重复读写，更多 token 不保证更高成功率 | 强 | How Agents Spend、SWE-agent、EET |
| 任务相关、结构保持的上下文裁剪可以兼顾质量与 token | 强 | SWE-Pruner；RepoCoder/CoCoGen 提供机制支持 |
| 提前终止、失败隔离、选择性重试优于无界循环 | 中强 | EET、Runtime-Structured、Reason-Code |
| 所有任务都先做重规划并非最优 | 中 | PaT、Reason-Code；仓库级仍需验证 |
| 固定流程可提高稳定性和成本可控性 | 中 | Agentless、PatchPilot |
| 清晰、短而自包含的任务描述更有利于成功 | 中 | Issue Ready、HULA；主要是关联证据 |
| 欠规格时澄清能提高质量，但未证明省 token | 中 | Ambig-SWE、HULA |
| 通用 Prompt 压缩可直接用于源代码 | 弱/存在反例 | SWE-Pruner 对 LLMLingua2/RAG 的代码场景反例 |
| 多 Agent/更多分解天然更省 token | 不支持 | Tokenomics 的通信成本；Runtime-Structured 的静态分解反例 |
| 精心编写的聚焦 Skill 可以提升任务成功率 | 强 | SkillsBench；Wild Skill 研究提供现实检索边界 |
| 使用 Skill 天然减少端到端 token | 不支持/结果异质 | SkillsBench 的 18 配置 token 结果有增有减 |
| Skill 渐进披露能减少其自身上下文开销 | 强 | SkillReducer |
| 完整 Skill 已被证明可同时消除三类 Coding Agent 浪费 | 证据缺口 | 现有 Skill 研究与 Coding Agent 效率研究尚未完成该整合验证 |
